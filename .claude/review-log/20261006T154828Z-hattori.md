### M1. `main_id` vem de duas fontes; a validada não é a persistida, e há um default `""` inventado
- `ingestion/connector/simbad/SimbadConnector.java:110-111`: `String mainId = t.oname() == null ? "" : t.oname();`
  vira `SourceObjectRef.mainId` e também `ResolvedName.matchedIdentifier` (os dois campos guardam o mesmo valor).
- `ingestion/pipeline/NormalizedToCatalog.java:34` grava `o.ref().mainId()` (o `oname` do **Sesame**) como `ObjectWrite.sourceMainId`.
- Já `SimbadMapper.java:112` e `SimbadValidator.validateBasic` usam e validam o `main_id` do **TAP basic**
  (o objeto é rejeitado se ele faltar), mas esse valor só alimenta o rótulo e a `sourceObjectUrl`.
- Por que importa: o mesmo fato vem de dois payloads. O que chega ao `DisplayNameRule` é o menos validado
  (o Sesame responde "from cache"), e quando ele falta o código põe `""` em vez de ausência. Hoje
  `ObjectWrite.requireNonNull` deixa o `""` passar, e o `DisplayNameRule` só falha mais adiante, na gravação.
  Isso contraria a regra central e já confunde a leitura.
- Correção:
  ```java
  // NormalizedObject ganha o main_id do payload que de fato foi validado
  public record NormalizedObject(SourceObjectRef ref, String mainId, List<String> queries, ...)
  // SimbadMapper.toObject
  return new NormalizedObject(name.ref(), mainId /* basic.main_id */, name.queries(), ...);
  // NormalizedToCatalog
  new ObjectWrite(o.ref().source(), o.ref().sourceRef(), o.mainId(), ...);
  // SimbadConnector.resolve: sem default inventado
  String oname = t.oname(); // pode ser null; use só em log/diagnóstico
  ```
  Remova `ResolvedName.matchedIdentifier`, que duplica `ref.mainId`, ou deixe-o como `Optional<String>` só de diagnóstico.

### M2. Parte dos extratores do `SimbadMapper` descarta valor da fonte em silêncio, e um caso gera motivo de ausência falso
- `SimbadMapper.java:163-166` (paralaxe): `plx_err` negativo vira `null` **sem issue**. O efeito é real e visível:
  `DistanceFromParallax` devolve `NO_UNCERTAINTY` e a API mostra "Paralaxe sem incerteza publicada".
  Isso é falso, porque a fonte publicou uma incerteza (inválida). Compare com `rvz_err` (linhas 187-190) e `flux_err` (255-258), que registram issue.
- `TapRow.number()` devolve vazio tanto para null quanto para texto não numérico. Só `magnitudes` (240-243)
  e `distances` (275) distinguem os dois casos. Em `plx_value` (159), `rvz_redshift`/`rvz_radvel` (174-175),
  `galdim_*` (224) e `minus_err`/`plus_err` (293-294), um valor presente e não numérico some sem issue.
- Por que importa: a ausência deixa de ser explícita. O `error_summary` do run não mostra que a fonte mandou algo que foi descartado.
- Correção: um helper só, usado por todos os extratores.
  ```java
  private static Optional<Double> numeric(TapRow row, String column, String label, List<String> issues) {
      Optional<Double> n = row.number(column);
      if (n.isEmpty() && row.text(column).isPresent()) {
          issues.add(label + ": " + column + " descartado: valor nao numerico '" + row.rawText(column).get() + "'");
      }
      return n;
  }
  private static Double nonNegativeError(TapRow row, String column, String label, List<String> issues) {
      Double err = numeric(row, column, label, issues).orElse(null);
      if (err != null && err < 0) { issues.add(label + ": " + column + " negativo descartado: " + err); return null; }
      return err;
  }
  ```
  Com isso, `SimbadValidator.checkError`, cuja mensagem hoje é descartada e reescrita na linha 256, pode sair.

### m1. Classificação de resposta HTTP duplicada (TAP x Sesame), com divergências
`HttpTapClient.java:76-98` e `HttpSesameClient.java:55-69` repetem a mesma regra:
429/5xx vira Unavailable, outros não-2xx viram Query, `ResourceAccessException` vira Unavailable. E já divergem:
o Sesame não protege `getBody()` nulo e não inclui o corpo abreviado na mensagem, o que tira contexto do erro.
Extraia para `ingestion.connector`:
```java
static void throwIfFailed(String service, HttpStatusCode status, String body) {
    if (status.value() == 429 || status.is5xxServerError())
        throw new SourceUnavailableException(service + " respondeu HTTP " + status.value() + ": " + abbreviate(body));
    if (!status.is2xxSuccessful())
        throw new SourceQueryException(service + " recusou a consulta (HTTP " + status.value() + "): " + abbreviate(body));
}
```

### m2. A detecção de truncamento por MAXREC está no conector específico, e o JSON é parseado duas vezes

### m12. `dataset` tem três significados
É o rótulo de `raw_payload` (`DS_BASIC`), o pedaço da chave de `measurement` (`"mesDistance:<bibcode>:<method>"`)
e também o nome de tabela TAP (`COLUMNS_BY_TABLE` e `TABLES` em `SimbadQueries` usam as constantes `DS_*`
como nomes de tabela). Separe com `TABLE_BASIC = "basic"` etc. e deixe `DS_*` só para rótulos de payload.

### m13. Tipo do SIMBAD vazando para o contrato genérico
`SourceObjectRef.sourceInternalId` é `long` (o oid), mas o V2 diz que `source_ref` será `pl_name` ou `spkid`,
que são texto. No Bloco 2 o contrato vai ter de mudar, e todos os consumidores com ele.
Faça o contrato carregar `String sourceRef`. O oid numérico fica interno a `connector.simbad`:
`Long.parseLong(ref.sourceRef())` em `fetch`/`normalize`, ou um mapa no `FetchedBatch` do SIMBAD.

### m17. Um run que não fez nada termina `ok`
