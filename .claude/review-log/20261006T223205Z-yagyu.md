## MINOR

### r1 — Retencao de raw_payload usa `records_ok = 0` como "nao gravou objeto", o que e falso para run interrompido
- Onde: `RawPayloadRepository.deleteForUnproductiveOnDemandRunsBefore` +
  `IngestionRunRepository.failDangling`.
- Vetor: cada objeto e gravado em transacao propria, entao um run on_demand derrubado no meio
  (restart) pode ter measurements commitados apontando para seus payloads, mas `failDangling` so
  muda status — `records_ok` fica 0. Apos 30 dias a retencao tenta apagar esses payloads.
  Hoje `measurement.raw_payload_id` e FK sem ON DELETE (NO ACTION), entao o DELETE inteiro falha:
  NAO ha perda de proveniencia, mas a purga de payloads passa a falhar toda hora (para de
  funcionar para todos, nao so para aquele run), reabrindo parcialmente o m2. E a protecao da
  proveniencia depende so da FK — se alguem a trocar por `ON DELETE SET NULL/CASCADE`, vira perda
  silenciosa de proveniencia do catalogo.
- Correcao: trocar o criterio por existencia real de referencia:
  `AND NOT EXISTS (SELECT 1 FROM measurement m WHERE m.raw_payload_id = p.id)` (pode manter
  `records_ok = 0` como filtro adicional ou remover). Teste de integracao com run on_demand
  `failed` por `failDangling` que tem measurement referenciando payload.
